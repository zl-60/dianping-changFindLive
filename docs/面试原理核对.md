> **历史版本提示：** 本文核对的是 2026-10-11 原点评及第一阶段代码，其中“尚未实现”的结论不能直接用于第二阶段。当前实现与面试边界请阅读 [第二阶段问答手册](宠伴生活-Java后端实习面试问答手册.md) 和 [第二阶段官方资料核对](Java面试官方资料核对-第二阶段.md)。

核对日期：2026-10-11。依据当前源码和官方资料；这里只做静态分析，没有连接 Redis、RabbitMQ 或数据库。项目使用 Spring Boot 2.3.12；引用的新版本文档用于核对这些长期稳定的原理，不代表项目已经升级。主项目源码位于 `D:/dianping-master/dianping-master`。

## 1. Redis Lua 为什么适合秒杀资格判断

业务场景：多人同时抢同一张券，需要把查库存、查重复、扣库存、记录购买资格连成一个不能被其他请求穿插的操作。Lua 在 Redis 内执行，减少网络往返，并保证脚本执行期间其他客户端命令不穿插。它解决的是 Redis 范围内的并发竞争，不能把 Redis、RabbitMQ、MySQL 自动变成一个事务。[Redis 官方 Lua 文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)

面试口述：我用 Lua 将库存判断、用户去重和预扣库存放在 Redis 服务端执行，避免多个请求分别 GET、判断、DECR 时发生竞争。预扣成功只代表请求获得资格，订单持久化还要由后续链路确认。

注意：原子执行不等于运行时失败自动回滚。Lua 后半段命令报错，前面已经执行的写入不会自动撤销；应在写入前校验类型和参数，必要时做补偿。[Redis 官方回滚说明](https://redis.io/blog/you-dont-need-transaction-rollbacks-in-redis/)、[Redis Lua 调用与错误处理](https://redis.io/docs/latest/develop/programmability/lua-api/)

当前源码边界：

- `src/main/resources/seckill.lua:33` 先扣库存、再 SADD，最后 XADD。若 XADD 因 key 类型错误失败，不能认为前面的扣库存会回滚。
- 脚本成功分支没有 `return 0`，Java 的 `seckillVoucher` 将 null 当作成功。应明确约定成功和失败返回码，缺库存的 `-1` 当前也被误报成“不能重复下单”。
- Java 传空 KEYS，脚本根据 ARGV 拼接 key。官方要求把访问的 key 通过 KEYS 明确传入；迁移 Redis Cluster 时还要规划相关 key 的同槽问题，当前方案不能直接宣称支持集群。
- 当前成功脚本同时写 `stream.orders`，随后 Java 再发 RabbitMQ；Stream 消费代码已经注释，遗留 Stream 可能持续积累。应选定主消息通道，不能把两个机制当成已完整实现的双保险。

## 2. Redis Stream 的 pending 是什么

消费组收到消息后，未确认的消息进入 PEL。`XACK` 从 PEL 移除记录，并不等于从 Stream 删除消息。`XREADGROUP ... >` 读未投递的新消息；用 `0` 读取当前消费者自己的历史 pending；接管其他宕机消费者的消息要使用 XCLAIM/XAUTOCLAIM 等机制。[Redis XREADGROUP 官方文档](https://redis.io/docs/latest/commands/xreadgroup/)、[Redis XAUTOCLAIM 官方文档](https://redis.io/docs/latest/commands/xautoclaim/)

项目里的 `VoucherOrderHandler` 和 `handPendingList` 是被注释的演进代码。它表达了“处理后 ACK、异常重读 pending”的思路，但不能说当前服务正在用 Stream 消费组保证可靠消费。即使恢复代码，也应在启动时处理遗留 pending，并处理跨消费者接管、有限重试和永久失败；仅在新消息处理抛异常后读 pending，不足以覆盖所有重启场景。

## 3. RabbitMQ 两种确认解决不同问题

Publisher confirm 解决生产者到 Broker 的确认；consumer ack 解决 Broker 到消费者的处理确认。二者彼此独立。生产者收到 confirm 不代表消费者已写入 MySQL；消息被重复投递时还需要业务幂等。无法路由的消息还应结合 mandatory/return 处理，不能只看发送方法没有抛异常。[RabbitMQ 官方确认文档](https://www.rabbitmq.com/docs/confirms)

Spring AMQP 的 AUTO 表示监听容器按监听方法返回或异常决定确认，不等于业务代码显式 `basicAck`；MANUAL 才要求应用自行确认。配置和容器实现会影响异常后的重排队行为。[Spring AMQP 监听容器官方文档](https://docs.spring.io/spring-amqp/reference/amqp/containerAttributes.html)

源码证据和影响：

- `VoucherOrderServiceImpl:236` 只有 `convertAndSend` 和同步异常捕获；仓库配置及 Java 代码中未找到 confirm/return 配置、回调、重试闭环或预扣补偿。外部部署可能有额外配置，因此结论限于仓库。
- `SeckillVoucherListener:37` 先保存订单再扣数据库库存，两个监听方法都没有包住整体流程的事务，也没有校验扣库存的 boolean 结果。即使单条 SQL 各自成功，也不能保证两步一起提交；可能出现订单已保存但库存未扣。
- 同订单主键重复能触发主键约束，却不等于完善幂等：第一次保存成功、扣库存前异常，重试可能被重复主键挡住，库存仍没扣。应该在同一事务中做订单幂等和库存更新，并识别“已完成”与“部分完成”。
- `hmdp.schema.sql` 的 `tb_voucher_order` 只有订单 ID 主键，没有 `(user_id,voucher_id)` 唯一约束；不能说数据库已兜底保证同一用户同一券只下单一次。

可作为改进回答：将消费处理放入独立事务 Service；先用订单 ID 或业务唯一键判重，数据库条件扣库存必须检查影响行数；提交后再确认消息；明确失败状态、有限重试与人工处理。生产者侧使用消息确认、可追踪的发送记录及补发/补偿，处理 Redis 预扣成功但发消息失败的窗口。它们是建议，当前仓库没有完整落实。

## 4. TTL 和死信队列不等于订单超时关闭

项目 `QueueConfig` 给 QA 设置 `x-message-ttl=10000`，并将死信路由到 Y/QD。这个 TTL 控制的是消息在队列中的存活时间，不能保证订单创建 10 秒后触发取消。QA 有正常消费者，消息可能立即被消费；QD 消费者的实际逻辑也是保存订单、扣库存，并没有取消订单。[RabbitMQ 官方 TTL 文档](https://www.rabbitmq.com/docs/ttl)

死信常见触发包括消息过期、拒绝且不重排队、队列超过长度限制等。消费抛异常是否进入死信还取决于容器异常策略；若一直 requeue，则可能反复回原队列。[RabbitMQ 官方死信文档](https://www.rabbitmq.com/docs/dlx)

面试口述：当前我配置了过期消息的死信路由，并写了死信消费者；但它目前用于继续落单，尚未实现订单超时关单。若要实现关单，需要独立延迟检查消息，到期查询订单状态，并在事务内取消未支付订单和恢复库存。

## 5. Spring 事务：代理调用与线程边界

默认代理模式下，只有经代理进入的方法调用才会触发事务；同对象内部 `this.xxx()` 调用不会因被调方法有注解就启动事务。传统 PlatformTransactionManager 的事务绑定当前线程，不自动传到线程池或 MQ 消费线程。异步消费者需要在自己的线程通过 Spring 代理调用事务方法。[Spring 官方事务注解说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)、[Spring @Transactional 官方 API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/annotation/Transactional.html)

当前项目有一个 `@Transactional createVoucherOrder`，其中会查重复、条件扣库存、保存订单；但是 RabbitMQ 消费者没有调用它，而是直接分别调用 save 和 update。不能用这个未走到的方法证明当前消费链路有完整事务。

`handleVoucherOrder` 使用 Redisson 锁并调用 `proxy.createVoucherOrder`，但给 proxy 赋值的代码已注释；若直接启用旧处理链而不恢复代理初始化，这里会空指针。更清楚的设计是拆成独立的事务订单 Service，由消费者调用；事务在消费者线程开启，锁覆盖事务方法执行至提交完成。

默认情况下 RuntimeException/Error 会触发回滚，普通受检异常不会；吞掉异常或正常 return 也不会自动回滚。[Spring @Transactional 官方 API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/annotation/Transactional.html)
